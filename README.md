半導體晶圓良率異常預警與根因排查（POC 實作筆記）
宣告：這是我自己拿公開資料集（UCI SECOM）練習與驗證思路的 Side Project，程式碼跟實驗數據全部都是開源資料，沒有碰任何公司的機密。

1. 這份練習想解什麼問題？
不良品少得可憐： 瑕疵品（Fail）佔比不到 7%，正負樣本大概 1:14。如果直接無腦套一般模型，模型全部猜正常準確率就有 93%，但實際上瑕疵一個都抓不到。

欄位又多又髒： 590 個感測器數值，一堆欄位空了一大半，不然就是整欄數值都一樣（根本沒在動），雜訊非常重。

工程師不收黑盒子： 如果只跟產線說「這批貨有 85% 機率會壞」，對方根本不知道從何查起；一定要明確點出「到底是哪幾號感測器數值飄掉了」，才有實質排查意義。

3. 實作踩坑與實驗心得
不要隨便用 SMOTE 硬造假資料：

一開始想說樣本少，用 SMOTE 補點異常樣本，結果在 500 多維的空間裡生出來的點很多都落在模糊地帶，害假警報（False Positive）暴增快三成。後來發現老老實實在 LightGBM 裡調 scale_pos_weight（加重看漏壞品的懲罰）穩定多了。

先大刀砍欄位，跑得快表現還沒掉：

算了一下發現有 110 多個感測器不是常數就是缺值超過一半。乾脆在進模型前直接濾掉，訓練速度快了快一半，預測分數完全沒跌，還順便幫樹模型減肥。

看 ROC-AUC 會自我感覺良好：

在這種極端不平衡的情境下，ROC-AUC 隨便跑看起來都很高，但實際上抓壞品的能力可能很差。自己看成果時主要盯著 PR-AUC 跟「如果一天產線只能排查最可疑的前 5% 機台，能抓到多少比例的壞品」。

4. 還沒做完 / 未來能改進的地方
[ ] 機台會老化：目前把每一筆晶圓都當成獨立事件，但實務上感測器數值應該有時間連續性，之後想試試補算滾動平均（Rolling Mean）之類的趨勢特徵。

[ ] 跑速問題：現在是整包丟進去離線算，如果要接到產線做即時預警，推論時間得壓在幾十毫秒內，特徵前處理的寫法可能要換成更快的寫法（比如 Polars 或 C 擴展）。
